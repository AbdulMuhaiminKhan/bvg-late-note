# Security review

## Who can access what

| Who | Can reach | How it is enforced |
|---|---|---|
| Anyone on the internet | the web pages (read delays, make a note) | Container Apps ingress (HTTPS) only. The VM has no public IP. |
| Me (admin) | the VM through `az vm run-command`, psql to the database | Azure sign-in + RBAC on the resource group (no SSH port open anywhere); database firewall rule for my IP |
| The collector job | the database and one Key Vault secret | its managed identity has only "Key Vault Secrets User" on this vault |
| The Container App | the database and one Key Vault secret | same, with its own identity |
| The VM | the database and two Key Vault secrets (database URL, MQTT password) | same, with its own identity; inbound only ports 80/8000/1883 from inside the VNet |
| MQTT clients (sensor, subscriber) | the Mosquitto broker on the VM | username + password required (`allow_anonymous false`); port 1883 reachable only inside the VNet, never from the internet |
| Everyone else | nothing else | NSG default deny from the internet; database only accepts Azure IPs and listed IPs, and needs the password over TLS |

## Where the secrets live

There are two secrets: the database connection string and the MQTT broker password.

- It is **generated** by `infra/02-database-and-keyvault.sh`, stored in **Key Vault**
  and never printed, committed or baked into an image.
- The collector job and the Container App read it at runtime with **managed identities**
  (no passwords in their settings, only a Key Vault reference).
- The MQTT password is generated by `infra/05-deploy-on-vm.sh` straight into Key Vault. On the VM,
  Mosquitto only keeps its hash (`mosquitto_passwd`).
- On the VM both live in `/etc/latenote.env` (root-only, `chmod 600`). The VM fetches it itself
  from Key Vault with its managed identity; it is never put into a run-command script,
  because those scripts are stored in Azure.
- Locally it is in `.env`, which is git-ignored. `.env.example` has only placeholders.
- CI publishes the image with GitHub's short-lived workflow token: no stored secrets.

## What is protected

- Database not reachable from the internet except from my own IP and from Azure IPs (see below), always with TLS (`sslmode=require`).
- No SSH port and no public IP on the VM: it is reachable only inside the VNet, and administered with `az vm run-command`.
- HTTPS for the main app (Container Apps).
- Container runs as a non-root user; secrets are not in the image.
- The web app sends security headers (no framing, no MIME sniffing, a strict content security policy).
- Notes are not guessable: random 8-character codes.
- The delay on a note comes from data the system collected itself, not from user input, so a user can't type in a fake delay.

## What is not protected (honest list)

- **The VM serves plain HTTP** on port 80, but only inside the VNet. Fine for the IaaS comparison, not for real users.
- **No user accounts and no rate limiting**: anyone can create many notes.
- **MQTT without TLS** inside the VNet: the login is sent in plain text on the private network. Fine for a private subnet, but a real IoT deployment would use port 8883 with TLS (or Azure IoT Hub / Event Grid MQTT).
- **The database has a public endpoint.** The "allow Azure services" rule lets any Azure IP try to connect, including other customers' services; only the password and TLS stop them. Private networking (VNet integration and a private endpoint) would be safer but costs more than this free-tier setup allows.
- **The BVG API is a free community service** with no guarantee: if it goes down, no new delays are recorded (old notes still work).
- A note proves *the train* was late, not that *the person* was on it.

## What I would do next

1. Private endpoint for PostgreSQL and VNet integration for Container Apps.
2. Rate limiting on note creation (for example, Azure Front Door or a simple per-IP limit).
3. Retire the VM, or put it behind the Container Apps environment in the same VNet.
4. Alerts in Azure Monitor when the collector job fails several runs in a row (needs Log Analytics, left out to stay free).
